# Defending Wand Horizon: the questions a tester can ask, and honest answers

How to use this: read a section, close it, and answer each question out loud in your own words. Every answer says **what to say**, **where it is in the code** (so you can show it), and **what not to claim**. The honest answer is always the strong one: the project is deliberately a browser simulation, and everything below is true of the code as submitted.

Numbers to know cold: **50 people, 500 AI workers, 8 teams, 9 missions, 7 conflicts, 106 operations, 340 audit events** in the seeded data; **4 System screens**; **147 tests**; **2 runtime dependencies** (React and React DOM).

---

## 1. Data: where it lives and why

**Q1. How is the data stored, and why?**
- *Say:* "It isn't stored anywhere permanent. The whole state is one JavaScript object held in memory by React (`useState` in `AppProvider`, `src/state/store.tsx`). On load it is generated by `createInitialState()` (`src/data/generate.ts`). A refresh or the Reset demo button returns it to the same starting point."
- *Why:* the challenge is to show the logic of visibility and accountability, not to run infrastructure. With no backend, anyone opens a URL and sees an identical, working product; nothing can be corrupted; the demo is repeatable.
- *Trade-off, say it before they do:* no persistence, one user, no real integration. In production the event log would live in an append-only store (a database table that only allows inserts).
- *Don't claim:* that it is "a database", or that data survives a refresh.

**Q2. So where does the data come from? Is it real?**
- *Say:* "All synthetic. A seeded random generator (`mulberry32` in `src/data/prng.ts`) and a fixed 'now' (26 Oct 2026, 14:00 UTC) mean every load produces exactly the same 550 workers, missions, conflicts and operations."
- A few hero scenarios are written by hand (the blocked $2.4M settlement, the wire whose permission was revoked) so the story is clear; the other ~100 operations are generated.
- *Don't claim:* any of it is a real company or measurement.

**Q3. How does the audit history exist if there's no backend and no past?**
- *Say:* "The history is produced by replaying scripted actions through the same reducer the UI uses (`createInitialState`, the 'replay' section). So seeded history, decisions and evidence are consistent with the live logic by construction, not hand-written."
- This is a strong answer: it means the fixtures cannot contradict the rules.

**Q4. Does it store anything in the browser?**
- *Say:* "Only two tiny UI flags: `localStorage` remembers that you dismissed the first-run strip, and `sessionStorage` remembers that the map already opened on the top issue this session. No cookies, no network requests for data (there is no `fetch` in the app)."
- *Where:* `Overview.tsx`, `MapView.tsx`.

**Q5. Why not a real database or API?**
- *Say:* "Scope and risk. Adding a backend would add more to defend than it proves for this challenge. The architecture keeps the door open: all state changes go through one pure function, `applyAction`, so a server could run the same function."

**Q6. What happens on refresh, and what does Reset demo do?**
- Both restore the original seeded data in memory. Reset clears every change you made (reassigned decisions, resolved conflicts, paused workers, permission changes, execution attempts, and the events they wrote), the simulated clock and the demo role. Nothing is sent anywhere.

## 2. Architecture and technology choices

**Q7. Why React, TypeScript and Vite? Why only two dependencies?**
- React for a component UI, TypeScript for strict typing of the domain (`strict`, `erasableSyntaxOnly`), Vite for a fast build. No router library, state library, UI kit or chart library: each would add more to explain than it saves at this scope. Everything else (the map, charts, replay, animations) is hand-built SVG, canvas and CSS.

**Q8. How is the code organized?**
- `src/domain/` pure TypeScript with no React: types, `authorize.ts` (permission rules), `reducer.ts` (the one state-transition function), `selectors.ts` (metrics and queries), `findings.ts` (issues), `audit.ts` (event wording), `orgLayout.ts` (map layout).
- `src/data/` the seeded fixtures. `src/state/` store, navigation, router. `src/ui/` screens and primitives. `tests/` 12 test files.
- *Why:* the rules can be tested without a browser, and the UI cannot bypass them.

**Q9. How does data flow?**
- One direction: UI calls `act(action)` → `applyAction(state, action)` returns a new state → selectors derive what to show → UI re-renders. The UI never mutates state, and no number on screen is stored: counts, totals and coverage are computed from the underlying records, so two screens cannot disagree.

**Q10. Why hash URLs (`#/system`, `#/demo`) instead of normal routes?**
- Direct loads and refreshes work on any static host with no server rewrite rules. It was also the simplest correct choice with no router dependency. The grammar lives in one file, `src/state/router.ts`, with tests.

**Q11. How is it deployed?**
- It is a static site built with `npm run build` (Vite output). The live site is on Vercel at `wand-horizon.vercel.app`. There is no server code. *If asked for details you don't know (build settings, region), say so.*

**Q12. Is it fast? Does it scale to 500 AI workers?**
- *Say:* "I measured before optimizing. Every derived calculation takes under 2 ms on the seeded data (the findings list 1.5 ms), so I didn't add a cache. The one real cost was download size, so the landing page now loads only 234 KB (74 KB compressed) instead of 431 KB, and the System, demo and brand film load only when opened."
- The map draws 550 nodes as SVG, which is fine at this size. *Don't claim* it scales to 100,000 workers; it would need virtualization and a server.

## 3. Mission 2: AI identity and responsibility (the strongest part)

**Q13. How do you prove what an AI worker was authorized to do at a specific moment?**
- *Say:* "Permissions are never stored as current state. They are rebuilt by folding an append-only log of `PermissionChanged` events (grant, modify, revoke) in order. To ask 'what was it allowed at moment X' I fold only the events up to X. That is `scopeStateAsOf` in `src/domain/authorize.ts`."
- *Why this matters:* there is no 'current permission' field that can drift from history, so history is correct by construction.

**Q14. What does "moment X" mean? Timestamps?**
- *Say:* "Order is by a global, strictly increasing sequence number (`seq`), not by timestamp. Timestamps can tie or be skewed between systems; a sequence number gives a total order, so reconstruction is deterministic." (Tested: `domain.test.ts` 'orders by seq even when timestamps tie'.)

**Q15. When is authorization checked?**
- At the instant a consequential action executes, not when the work was planned. Policy: authorization must be valid at execution time, and revocation before execution prevents the action.

**Q16. What exactly is stored for each execution attempt?**
- An `AuthorizationEvaluated` event with the operation, worker, permission, amount, decision (allowed or denied), a reason code (`ACTIVE_GRANT`, `NO_GRANT`, `REVOKED`, `LIMIT_EXCEEDED`), the cutoff `seq`, the resolved permission state, and the ids of the exact permission events it relied on. It is followed by either `OperationExecuted` or `ExecutionPrevented`.

**Q17. What if permissions change after the action ran? Do you rewrite history?**
- *Say:* "Never. Later changes add new events; they never edit earlier ones. The case page shows the stored decision, then 'Now', and states that the decision stands. The replay slider rebuilds past states but never changes the stored decision." (Tests: 'later permission changes never rewrite an earlier decision', `replay.test.tsx`.)

**Q18. How do I know the replay isn't just showing me something you saved?**
- *Say:* "There's a 're-check from the record' step (`replayMatches`) that recomputes the decision from the log and compares it with the stored one. It shows Verified or Mismatch. Every seeded decision replays." (Governance stats count them.)

**Q19. Who is accountable?**
- Every AI worker has an accountable human owner (`ownerId`). Every operation has an approver (`decisionOwnerId`). Every event records who acted (`actor`). The replay's accountability strip shows who recorded the change, the worker's owner, the approver at that point in the record, and who last set the authority.

**Q20. Show me an AI executing while its authorization changes.**
- Live: open **AI accountability** → the "Wire $480,000 to Halden Freight" case → **Change permissions** → Revoke → **Run execution step**. The step is prevented with reason "revoked", and the stored decision lists the permission state it used. Seeded: "Wire $120,000 to Northwind Escrow" has a limit change, a revoke, a denied attempt and a re-grant; the replay shows each step.

**Q21. What are the limits of this?**
- An operation is **one execution step**; "during an operation" means between its start and the execution attempt. AI identity is a stable worker id, role, team and owner; there are no credentials or model/version identity. The "Acting as" selector only sets the name recorded in audit events; it is not authentication. **This is a policy and audit design demonstrated in a browser, not production security.** Say this yourself; it is on the site too.

## 4. Mission 1: organizational intelligence

**Q22. How does it find problems? Are they hard-coded?**
- *Say:* "They are derived from live data every render (`findings()` in `src/domain/findings.ts`) and never stored. When you fix the underlying data (reassign a decision, resolve a conflict, pause workers) the finding disappears from every screen because the data no longer matches it."
- Five kinds: blocked decision, conflicting objectives, duplicated work, cost without verified value, permission changed after work started. Ranked by severity, then kind, then how many workers are touched.

**Q23. Scenario 1: how do you detect AI cost rising without value?**
- A mission is flagged when at least 5 active AI workers have no verified value and their modeled cost rose 25% or more against the previous 30 days. *Be upfront:* the previous-period cost is a **simulated** figure from the same cost model, labeled "simulated" wherever it appears. There is no real time series, and we don't present it as a measurement. We also show no AI "activity" metric because none exists in the data; cost is the signal.
- Action: "Pause N workers" writes a `WorkersPaused` event, lowers the run-rate and the finding clears.

**Q24. Scenario 2: conflicting or duplicated work?**
- Seven seeded conflicts, two kinds: **duplicate** (two workers do the same work) and **contradiction** (two missions pursue opposing outcomes, e.g. "Pay suppliers early" vs "Minimize idle cash" on one liquidity buffer). Resolve by choosing the authoritative worker with a note; the conflict closes everywhere.
- *Honest caveat:* all conflicts are between two AI workers; people appear as their accountable owners.

**Q25. Scenario 3: a critical operation blocked by an unavailable person?**
- "Release settlement batch SB-2291 ($2.4M)" is awaiting its approver, Elena Park, who is out of office until 31 Oct, with a deadline in 20 hours. It is flagged only because the approver is actually unavailable. The panel names the person, the deadline, the business consequence (a synthetic sentence), the mission at risk, and any other operations waiting on the same person. Action: move the decision to an available person; moving it to someone also out of office is refused. The operation stays "awaiting approval" because the new person still has to decide.

**Q26. Why do you separate verified, estimated and unmeasured value?**
- Because blending them would overstate proof. Verified = confirmed in a system of record; estimated = model-based; unmeasured = no data. They are never added, and the **return on cost uses verified value only** (estimated value never counts), on synthetic data; no savings or profit is calculated. Coverage ("58% of AI workers have verified value") counts workers, not dollars.

**Q27. What is "blocked"?**
- An operation is blocked exactly when its status is `awaiting_approval`. It is a derived fact, not a separate field.

### Return on cost

**Q26b. How do you decide whether a worker is good or bad money-wise?**
- *Say:* "Return on cost: verified value divided by modeled monthly cost over the trailing 30 days (`src/domain/roi.ts`). Green is 3× or more, amber 1× to 3× or only estimated value, red under 1× or no verified value with cost rising 25%+, grey no value data. Estimated value is shown beside it and never counted. A person gets the roll-up of the AI workers they own, since value records attach to AI workers only."
- *Where:* Start here (company return, colour counts, 'See who to review'), Registry (Return column, filter, pause bar), worker profile.
- *Don't claim:* it is a real measurement. The value and cost are synthetic, the previous-period cost is simulated, and the thresholds are a policy constant.

## 5. Product and design decisions

**Q28. Why did you rename and simplify the interface?**
- First-time users hit eight stacked cards and internal vocabulary. The System now opens on three plain questions (Is anything stuck? Is the AI spend justified? What was the AI allowed to do?), each leading into one of the two missions; detail sits under "More detail". Screens are named for the question they answer (Start here, Needs attention, Org map, AI accountability).

**Q29. Why a map?**
- The org chart shows who reports to whom but not where work and AI sit. The map draws each team as a region and each person with the AI workers they are accountable for, so a problem is visible in context. It is a deterministic layout (not a force graph, which would be a hairball and change every load), and findings drive the camera.

**Q30. Why is the landing page black and the System light?**
- The landing, demo and brand film are a marketing surface in the logo's colors (black and lilac); the System is a working tool where dense data reads better on a warm light ground. They share the logo, type, the italic accent phrase, pill buttons and hairline borders. Colour in the System carries meaning: violet for interaction and verified value; red and amber only for severity.

**Q31. Is it accessible?**
- Honest answer: partly. Text pairs are tested for WCAG AA contrast, controls are real buttons with labels, focus is visible, motion respects reduced-motion settings, and the findings list and registry are the keyboard path. *Known limits:* individual AI dots on the map are mouse-only, and map labels are small at overview scale.

## 6. The demo, the film and the email

**Q32. Is the demo a video?**
- No, and we say so on the page. It is a scripted walkthrough that drives the real application inside an iframe, with a scripted cursor, real clicks and captions, so every number shown is the product's own. Reason: no recording tool was needed, it is deterministic, and it can't go out of date silently, because a test (`demo-integrity.test.tsx`) runs the whole script against the real app and fails if an element it needs is missing.

**Q33. The brand film?**
- A 22-second canvas animation that is a pure function of time, with sound synthesized in the browser (Web Audio, no audio files). Sound is off until the user presses "Turn sound on" because browsers block autoplaying audio. It is an illustration, not product data.

## 7. Quality, testing and honesty

**Q34. How do you know it works?**
- 147 automated tests: the authorization rules (revoke mid-flight, limit exceeded, ordering by seq, history never rewritten), the fixtures, findings, map layout, the UI flows (reassign, resolve, change permission then run), the replay, routing, contrast ratios, and the demo-integrity test. CI runs typecheck, lint, tests and build on every push. Lint is clean.

**Q35. What would you do differently or next?**
- Real persistence (an append-only store with a hash chain), real authentication and server-side enforcement, multi-step operations, real activity and cost time series, human-vs-AI conflicts, a separate investigator experience. Also split the largest files and move display text out of the domain layer (planned, not done).

**Q36. Did you use AI to build it?**
- It was built with Claude Code, with a design-review skill used for critique. Answer in your own words and honestly; be ready to explain any part, which is what this document is for.

**Q37. What is simulated and what is real?**
- *Real:* the authorization logic, the append-only log, the replay, the findings derivation, every number's arithmetic, the tests. *Simulated:* all people and data, the previous-period cost, missions and availability, the acting-as roles, the clock (each action moves 2 minutes forward). Nothing is production security.

## 8. Live-demo cheat sheet

Three clicks per mission from **Start here**:
- **Stuck:** "Investigate the most urgent" → "Move the decision" (pick someone available) → the finding clears and the count drops from 8 to 7.
- **Spend:** "Review the spend" → "Pause 14 workers" → run-rate falls, workers drawn as paused.
- **Allowed:** "Replay a past incident" → press Play or Next → read "Authorized then" beside "Permitted now".
- **Live mid-flight:** AI accountability → Wire $480,000 case → Change permissions (Revoke, any reason) → Run execution step → prevented.

If anything looks off: **Reset demo** (left rail) or refresh. If the live site is slow, `npm run dev` runs it locally.

## 9. Traps to avoid

- Don't call it "production-ready", "secure", or say the AI cost trend is measured.
- Don't present the return as a real measurement: it is verified value over *modeled* cost on synthetic data, with thresholds (3× and 1×) that are a policy setting. Don't say savings or profit.
- Don't say it uses a database or an API.
- If you don't know something (hosting settings, a file you didn't write), say "I'd have to check", then open the file. Every claim above names where to look.
